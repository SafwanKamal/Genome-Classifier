## Timing change and verification

The previous full routed design failed setup: **-0.812 ns WNS, -322.479 ns TNS,
1,666 endpoints**. Its activation-selector-to-DSP path had 5.436 ns data delay,
of which 4.198 ns was routing. Board packet success did not establish timing
closure.

The fix selects four input bytes within each of four activation quarters
using a registered 16-way selector, then selects the quarter using a 4-way
selector in the next existing read cycle. All 128 first-stage selection bits
remain physical registers after synthesis, without `keep` or `dont_touch`.
No extra read cycle, model repacking or multiplier changes were introduced.

- Core simulation: **1,000/1,000 golden scores**, **635 cycles**, unchanged.
- Core-only 5 ns synthesis: **+0.357 ns setup, +0.079 ns hold**, no failures.
- Resources: **5,003 LUTs, 8,123 registers, 16.5 BRAM tiles, 128 DSPs**.
- Synthesized quarter-register-to-DSP worst path: **+1.825 ns slack**, one LUT
  level; see `reports/model_v4_200_activation_selection_timing.rpt`.

**Full routed timing for this revision remains to be verified by the user.**
The existing implementation report is for the old selector. Reset synthesis
and rerun Synthesis and Implementation in the existing project. Verify the
core clock is 200 MHz/5 ns, setup WNS is nonnegative, TNS is zero, setup/hold
failing endpoints are zero, and internal endpoints have constraints. Generate
and program a new bitstream only after timing passes.

## Four-credit buffering verification

The existing two parser banks and two RX frame banks are sufficient for the
strict four-credit schedule tested here. No buffers were added to production
RTL. Do not infer support for windows above four.

The new test sends 1,000 variants in full batches followed by 1,000 in mixed
32/7/3/1-record batches, including consecutive single-record requests. It
temporarily gates classifier acceptance until all four request storage slots
are occupied, then refills only upon complete reply reception. It uses minimum
Ethernet gaps, wraps banks repeatedly, and checks request rejection for bad
CRC, marker, count and truncation.

**PASS: 2,000 exact scores in 98 replies; maximum outstanding batches 4.**
Both parser and RX banks reached full occupancy; 249,864 RX backpressure
cycles were observed without RX overflow, reply CRC/flag errors, missing
results or error LED. The test reply receiver uses existing two-bank capture
so minimum-gap short replies can arrive while earlier replies are decoded.
This is functional simulation with behavioral clocks, not routed timing or a
physical throughput measurement.

## Host implementation

The separate fast script receives original frame bytes via the existing
Scapy capture socket's `select` and `recv_raw` APIs. It does not construct and
then reserialize a Scapy packet. Request preparation and persistent raw-byte
sending are retained.

A decoded reply must have valid framing/flags, an expected pending sequence,
the expected count and no duplicate credit before returning its credit.
Replacement requests are sent before that reply's golden scores are compared.
All golden comparisons remain mandatory; a successful rate is published only
if all requested scores match. Duplicate/error runs exit unsuccessfully.

Timing is first send to last decoded reply, excluding preparation/startup and
final validation while earlier golden checks overlap transfer. Diagnostic
statistics describe the raw receive path and retain the overlapping-duration
caveat. Identity records hostname, Python/Scapy versions, resolved interface,
socket backends, manifest/input hashes and `--design-label`. The label is
user-supplied and does not independently verify programmed firmware.

All **22 Ethernet batch software tests pass**, including nine new tests for
the fast script and its four-credit option. A 33-record, window-four dry run
passes without opening Ethernet. No physical gain is claimed yet.

## User board comparison commands

After fresh implementation passes timing and the revised board is programmed,
run from the repository root on the same desktop and Ethernet adapter.

Start with a small raw-receive smoke test:

```powershell
uv run --with scapy --with numpy --with pandas --with pyarrow python software/ethernet_batch_stream_rate_fast.py --interface "Ethernet" --count 100 --batch-size 32 --window 2 --sequence 9000000 --design-label "v4-200-quarter-mux" --report reports/model_v4_fast_smoke.json
```

Require all correct with zero missing/duplicates/mismatches. Then compare
three full runs of the original window-two script against the raw window-two
script, and finally raw window four. Keep the same revised bitstream for all
three configurations; this isolates host capture from credit depth.

```powershell
foreach ($runIndex in 1..3) {
    uv run --with scapy --with numpy --with pandas --with pyarrow python software/ethernet_batch_stream_rate.py --interface "Ethernet" --count 27477 --batch-size 32 --window 2 --sequence (10000000 + $runIndex * 100000) --report "reports/model_v4_selector_baseline_$runIndex.json"
}

foreach ($windowSize in 2,4) {
    foreach ($runIndex in 1..3) {
        uv run --with scapy --with numpy --with pandas --with pyarrow python software/ethernet_batch_stream_rate_fast.py --interface "Ethernet" --count 27477 --batch-size 32 --window $windowSize --sequence (11000000 + $windowSize * 1000000 + $runIndex * 100000) --design-label "v4-200-quarter-mux" --report "reports/model_v4_fast_w${windowSize}_$runIndex.json"
    }
}
```

Use medians without timing instrumentation for the primary comparison. Obtain
a separate diagnostic window-four run if all preceding runs pass:

```powershell
uv run --with scapy --with numpy --with pandas --with pyarrow python software/ethernet_batch_stream_rate_fast.py --interface "Ethernet" --count 27477 --batch-size 32 --window 4 --sequence 16000000 --timing --design-label "v4-200-quarter-mux" --report reports/model_v4_fast_w4_timing.json
```

The compute ceiling remains approximately 306,740 variants/s; the selector
fix does not reduce cycles. Raw reception and four credits aim to approach
that capacity, not guarantee it. CPU parity, power savings and end-to-end
application speedup remain unproven and require separate matched results.
